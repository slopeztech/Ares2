# Changelog — v2.7.2

**Date:** 2026-07-07  
**Type:** Patch — LoRa AUX flow-control regression fix (Radio, Driver)

---

## Summary

This patch fixes a regression introduced across two earlier commits that
permanently disabled AUX-pin flow control on the DX-LR03 LoRa module,
causing systematic packet loss during link tests and flight telemetry.

---

## Root cause

**Two-commit chain:**

1. **Commit `d1dd0f1`** (v2.something): Added `LORA_AUX_TIMEOUT_MS = 50` to
   `config.h` to make the AUX timeout configurable.  50 ms is far too short:
   - The DX-LR03 module self-test drives AUX LOW for ~1 000 ms after power-on.
     `begin()` called `waitReady(AUX_TIMEOUT_MS = 50 ms)`, timed out while the
     module was still initialising, and set `auxAvailable_ = false`.
   - Even if `auxAvailable_` somehow started as `true`, `send()` called
     `waitReady(50 ms)` for TX flow control.  The worst-case air-TX time at
     2.4 kbps is ~1 850 ms (see `TELEMETRY_RATE_MS` comment).  Any send attempt
     during an ongoing transmission would time out in 50 ms, set
     `auxAvailable_ = false`, and permanently disable flow control for the
     session.

2. **Commit `a8a7eaa`** (v2.3.11 — P3-1, magic-number removal): Replaced the
   hardcoded `2000` in `waitReady()` with `AUX_TIMEOUT_MS / POLL_PERIOD_MS`.
   With `AUX_TIMEOUT_MS = 50`, this further reduced `MAX_AUX_POLLS` from 2000 to
   50, removing the last compensating protection.

**Net effect:** `auxAvailable_` was always `false`.  All UART writes to the
DX-LR03 were unconditional, with no flow control.  `TELEMETRY_RATE_MS = 2 000 ms`
provides only 150 ms of margin above the ~1 850 ms worst-case air-TX time.
Without AUX flow control, a timing variation or back-to-back transmission
(e.g. `on_enter` EVENT followed by HK at t = 2 000 ms) can push a new UART
write to the module while the previous over-air frame is still being transmitted,
causing the module to drop or corrupt the queued data.

---

## Fix

### `src/config.h`

Replaced the single `LORA_AUX_TIMEOUT_MS = 50` with two purpose-specific
constants that match the actual hardware timings:

| Constant                 | Value    | Purpose                                          |
|--------------------------|----------|--------------------------------------------------|
| `LORA_AUX_INIT_TIMEOUT_MS` | 2 000 ms | `begin()` wait for module self-test (~1 000 ms nominal) |
| `LORA_AUX_TX_TIMEOUT_MS`   | 3 000 ms | `send()` TX flow-control wait (worst-case air-TX ~1 850 ms) |

### `src/drivers/radio/dxlr03_driver.h`

- Added `AUX_INIT_TIMEOUT_MS` mapped to `LORA_AUX_INIT_TIMEOUT_MS`.
- `AUX_TIMEOUT_MS` now maps to `LORA_AUX_TX_TIMEOUT_MS` (TX flow control).
- Updated file-header AUX timing budget table.

### `src/drivers/radio/dxlr03_driver.cpp`

- `begin()` now calls `waitReady(AUX_INIT_TIMEOUT_MS)` so the 2 s init window
  is large enough for the ~1 s module self-test.
- `waitReady()` refactored: `pollsLeft` is now computed directly from the
  caller-supplied `timeoutMs` argument (`timeoutMs / POLL_PERIOD_MS`), capped at
  `MAX_AUX_POLLS` (derived from `AUX_TIMEOUT_MS`) for MISRA PO10-2
  bounded-loop compliance.  Previously, the static cap was the only source of
  the poll count, making the `timeoutMs` parameter partially ignored when
  called with values smaller than `AUX_TIMEOUT_MS` (e.g. the new
  `AUX_INIT_TIMEOUT_MS = 2 000 ms` call is now correctly bounded to 2 000
  polls, not 3 000).

## Verification

- Rebuild and flash; run `link_test.ams`: GCS should receive HK frames every
  2 000 ms with no gaps.
- Serial log should show:
  ```
  I LORA: DX-LR03 ready (baud=9600, AUX=GPIO9, flow_ctrl=on)
  ```
  (previously showed `flow_ctrl=off`).
- No `W LORA: AUX timeout during TX — flow control disabled` in the log.
