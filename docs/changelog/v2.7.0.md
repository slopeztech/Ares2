# Changelog — v2.7.0

**Date:** 2026-07-05  
**Type:** Performance + Bug Fix (Minor)

---

## Summary

This release closes the high-rate logging investigation started in v2.6.5.
Two independent bottlenecks were identified through hardware profiling
(`LOOP_TIMING_PROFILE_ENABLED`) and eliminated:

1. **STOR-2 — RAM write-behind buffer for CSV appends** — eliminates the ~80 ms
   per-row LittleFS flash program that limited logging to ~11 Hz.
2. **AMS-4.4.1 — Starvation-guard radio feedback loop** — fixes a bug where the
   HK/LOG starvation guard sent a blocking radio EVENT on every stalled tick,
   which itself caused the next tick to stall, locking the system at ~62 ms / tick.

Together these changes bring the achievable `log_every` rate from ~11 Hz to
**~70–75 Hz** on ESP32-S3 with an ADXL375 IMU, BMP280 barometer, and DX-LR03
LoRa radio at 9 600 baud.

---

## Changes

### Performance — STOR-2: RAM write-behind buffer (`LittleFsStorage`)

**Files:** `src/sys/storage/littlefs_storage.h`, `src/sys/storage/littlefs_storage.cpp`,
`src/config.h`

Root cause: every call to `LittleFsStorage::appendFile()` triggered a LittleFS
flash page program (~40–80 ms on ESP32 internal flash) because the internal page
cache is too small to hold even a single ~40-byte CSV row without committing.
Because the `ams_io` deferred-I/O task and the Arduino `loop()` task share
FreeRTOS priority 1, each flash program blocked the loop for the full duration.

Solution:
- **Open-handle cache** (`cachedAppendFile_`): the mission log file is opened
  once and kept open across consecutive calls to the same path.  Eliminates the
  ~15 ms `open()`/`close()` overhead per row.
- **RAM write-behind buffer** (`appendRamBuf_`, `AMS_IO_APPEND_RAM_BYTES = 4096`):
  rows are accumulated in a 4 KiB static buffer.  A single large `File::write()`
  is issued only when the buffer fills (~100 rows) or the durability timer
  (`AMS_IO_APPEND_FLUSH_MS = 1000 ms`) elapses.

The ~80 ms flash program cost is amortised over ~100 rows → **< 1 ms per row**.

Durability guarantees:
- Buffer is flushed before any `readFile` / `readFileChunk` / `fileSize` call on
  the same path — downloaded logs are always complete.
- Buffer is flushed on `end()` (unmount) and `flushCachedAppend()`.
- `invalidateAppendCacheIfPathLocked()` closes and flushes the cache when
  `writeFile`, `removeFile`, or `renameFile` touch the cached path, preventing
  stale file-descriptor state.

New config constants:
| Constant | Default | Description |
|---|---|---|
| `AMS_IO_APPEND_RAM_BYTES` | `4096` | Write-behind buffer size in bytes |
| `AMS_IO_APPEND_FLUSH_MS` | `1000` | Max age of buffered data before forced flush |

Internal helpers added: `openAppendCacheLocked`, `commitAppendRamBufLocked`,
`stageAppendRowLocked`, `flushCachedAppend`, `invalidateAppendCacheIfPathLocked`.

### Bug Fix — AMS-4.4.1: Starvation guard radio feedback loop

**Files:** `src/ams/mission_script_engine_runtime.cpp`,
`test/test_ams_integration/test_ams_flight_scenario.cpp`,
`docs/standards/ams_standard.md`

Root cause: the HK and LOG starvation guards called `sendEventLocked(WARN, ...)`
to notify the ground station when a slot was falling behind.  On a slow radio
link (LoRa at 9 600 baud), a single `sendEventLocked` call blocks the calling
task for the full frame transmission time (~50 ms for a 48-byte EVENT frame).

This created a self-reinforcing feedback loop:

```
log_every 10 ms  (target: 100 Hz)
  ├─ tick > 10 ms → starvation fires → radio EVENT (50 ms) → tick = 52 ms
  ├─ tick > 10 ms → starvation fires → radio EVENT (50 ms) → tick = 52 ms
  └─ ... pegged at ~62 ms / tick = ~16 Hz regardless of hardware capability
```

The bug was diagnosed using `LOOP_TIMING_PROFILE_ENABLED`: the profiling trace
showed `I LORA: send(48): 50050 us` and `D AMS: EVENT frame sent seq=N` firing
every single tick with seq incrementing by 1 each time.

Fix: all four starvation guard sites (HK slot multi, HK legacy, LOG slot multi,
LOG legacy) now call `LOG_W` (serial, instantaneous) instead of
`sendEventLocked`.  The starvation warning is still available in the serial
monitor; the ground station detects missed samples from timestamp gaps or the HK
sequence counter.

Normative reference: `docs/standards/ams_standard.md` §AMS-4.4.1.

Test updated: `test_hk_slot_starvation_skips_samples` now asserts
`sendCount == 1` (HK only, no radio EVENT) instead of `sendCount == 2`.

### Performance — IMU I²C bus raised to 400 kHz

**File:** `src/config.h`

`I2C_FREQ_IMU_FAST_HZ` raised from 100 kHz to 400 kHz.  Both ADXL375 and
MPU6050 support I²C fast mode.  Rollback: set `IMU_I2C_USE_FAST_PROFILE = false`
to return to the conservative 50 kHz profile.

## Measured results (ESP32-S3, ADXL375 + BMP280, DX-LR03 LoRa @ 9 600 baud)

| Metric | v2.6.5 | v2.7.0 |
|---|---|---|
| `log_every 10 ms` actual interval | ~90 ms (11 Hz) | **~13 ms (75 Hz)** |
| Per-row `appendFile` cost | ~80 ms | < 1 ms |
| Starvation-guard radio EVENT per stalled tick | yes (50 ms each) | no |
| BARO interval | ~90 ms | ~100 ms |

---

## Notes

- RAM usage increased from ~73% to ~80% due to the 4 KiB write-behind buffer.
  If RAM pressure occurs, reduce `AMS_IO_APPEND_RAM_BYTES` to `2048`.
- The 30 s checkpoint stall (~150–250 ms) is unchanged; it is expected behaviour.
- `LOOP_TIMING_PROFILE_ENABLED` remains `false` in production builds.
