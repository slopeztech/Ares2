# Changelog — v2.7.3

**Date:** 2026-09-01  
**Previous version:** 2.7.2  
**Type:** Patch — security and documentation: authenticate-before-state anti-replay hardening (ARES-P0-001)

---

## Summary

This patch fixes an authenticated COMMAND denial-of-service weakness in the
radio dispatcher. A COMMAND with an invalid MAC could previously consume a
chosen sequence number because the mutable `SeqBitmap` replay window was
updated before HMAC and timestamp validation completed. A later legitimate
COMMAND using that sequence number would then be rejected as a replay.

The dispatcher now authenticates keyed COMMAND frames before any replay-window
mutation. Invalid MACs or stale/future timestamps return `HMAC_INVALID` without
consuming the sequence number, queueing the command, sending an acceptance ACK,
or creating reassembly state.

The release also reconciles the active APUS, architecture, SRS, source comments,
tests, and historical v2.3.4 wording around COMMAND authentication and timestamp
semantics.

---

## Security fix

### Root cause

`RadioDispatcher::handleCommand()` called
`rxSeqBitmap_.checkAndMark(frame.seq)` before `checkCommandMac()`. Because
`checkAndMark()` mutates the 64-slot sliding replay window, an unauthenticated
sender could reserve selected sequence numbers using frames with invalid tags.

### Corrected processing order

For a configured radio key, COMMAND processing is now:

1. Reject authenticated fragmented COMMAND frames while no whole-transfer MAC
   contract exists.
2. Require `FLAG_MAC` and verify the truncated HMAC-SHA256 tag in constant time.
3. Validate `CommandHeader.timestampMs` against receiver uptime using the
   wrap-safe +/-5000 ms freshness window.
4. Check and mark the authenticated sequence number in `SeqBitmap`.
5. Send the acceptance ACK and enqueue the command for priority-ordered
   execution.

Any failure in steps 1-3 returns `HMAC_INVALID` before mutable command state is
updated. Open mode remains backwards compatible when no key is configured.

## Tests

Two dispatcher tests lock down the corrected behavior:

| Test | Coverage |
|------|----------|
| `TC-AUTH-7` | Invalid MAC does not consume SEQ; a valid same-SEQ frame is accepted once; its authenticated replay is discarded |
| `TC-AUTH-8` | An unsigned COMMAND remains accepted when no radio key is configured |

Existing RFC 4231 HMAC vectors, timestamp-window cases, MAC failure cases, and
`SeqBitmap` wrap-around tests remain enabled.

## Protocol and requirements reconciliation

- COMMAND authentication is now normatively defined by APUS-4.8 through
  APUS-4.12. APUS-17 remains limited to PUS-C secondary-header adaptation.
- The canonical HMAC input, 16-byte key, 8-byte tag, `FLAG_MAC`, payload length,
  and constant-time comparison requirements are documented consistently.
- `CommandHeader.timestampMs` is defined as a ground-supplied estimate of
  receiver uptime, not independent sender uptime.
- NODE direction, COMMAND offsets, the 200-byte static payload limit, ACK/NACK
  failure codes, and authenticated-fragment rejection are aligned with the
  implementation.
- SRS-3006 through SRS-3010 add explicit requirements for MAC verification,
  authenticate-before-state ordering, freshness, open mode, and fragmentation.
- APUS-4.5 and APUS-4.6 now correctly report the existing retransmission engine
  as implemented.
- The legacy `pus_standard.md` copy is marked as a historical, non-normative
  snapshot; `apus_standard.md` is the active source of truth.

StrictDoc hygiene was also repaired by assigning unique UIDs to the background
task requirements, escaping two RST-sensitive C++ tokens, and restoring
sequential AMS section numbering.

## Compatibility and residual risk

- This patch does not introduce a new wire format. The 6-byte `CommandHeader`,
  timestamp field, `FLAG_MAC`, and 8-byte tag were introduced in v2.3.3-v2.3.4.
- Authenticated ground tools require no encoding changes for v2.7.3.
- Open mode remains available for development and bench use. Flight deployments
  must provision a radio key; fail-secure flight-mode enforcement remains
  pending under APUS-4.11.
- Authenticated fragmented COMMAND transfer remains unsupported and is rejected
  without creating reassembly state.
